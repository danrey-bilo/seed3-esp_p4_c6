# Испытания v0.2 — проверенный профиль 10 мс

18.09.2026. P4 rev1.3, ESP-IDF 5.5.5, TinyUSB 0.19.0~3,
Windows usbaudio2.sys, SPI 20 MHz, Seed3 как источник аудиочасов.

**PASS для перечисленных ниже проверок при WASAPI exclusive 10 мс и
запасе устройства 1 мс. Минимум Windows 3 мс доступен, но длинную проверку
на этом ПК не прошёл. Это не гарантия работы при любой нагрузке ПК.**

## Все форматы и минимальный буфер

Матрица `qualification-v2-min` прошла **20/20** коротких проверок анализатором
v2: 44,1 / 48 / 88,2 / 96 kHz, PCM16 и PCM24, capture-only и full-duplex,
с повторным переходом к 48k. Windows открыл все эти форматы.
После финального fault-injection и программного reset та же матрица с
рекомендованными **10 ms также прошла 20/20**, без ошибок позиции и фазы.

Драйвер сообщает минимум 3 ms. Тестер округляет вверх до целого кадра:
133 / 144 / 265 / 288 при 44,1 / 48 / 88,2 / 96 kHz.
Но следующий 60-секундный 48k прогон на минимуме **FAIL**: один скачок
devicePosition и подтверждённый фазой пропуск **288 frames / 6 ms**,
на frame 674640. См. `qualification-v2-48k/phase-steps.json`.
SPI/USB counters на P4 при этом не показали потерь. Это указывает на проблему
доставки/обслуживания буферов на стороне ПК, а не доказывает конкретный источник
задержки Windows. Короткая удачная матрица не отменяет отрицательный длинный тест.

В другой короткой попытке 48k/PCM16 на минимуме были 50 нулевых frames
(1,04 ms); строгий анализатор также отклонил её. Запас устройства оставлен
на 1 ms, но **для этого ПК рекомендуется WASAPI 10 ms**.
Можно выбирать меньший доступный период; устойчивость проверяйте в своём
приложении и под своей нагрузкой. Это не обещание сквозной задержки 10 ms.

## Нагрузка и восстановление

На 96k duplex по runtime counters P4:

| Метрика | Медиана | Наблюдаемый диапазон |
|---|---:|---:|
| Занятость core 0 | 18,4% | 16,0–20,4% |
| Занятость core 1 | 27,3% | 25,1–27,7% |
| USB task | 14,5% | 12,0–16,7% |
| SPI task | 27,2% | 25,0–27,6% |

Это scheduler estimates, не аппаратный profiler: ISR может учитываться
на счёте прерванной задачи. Проценты двух ядер не надо складывать как
загрузку одного ядра.

Seed при продолжающемся SPI/audio 96k сообщил **29,9% CPU**, в том числе
**11,3% audio callback**, capture_overruns=0 и spi_errors=0 до запроса.
Его UART `seed stats` читается только при закрытых USB streams: блокирующая
печать сама может вызвать пропуски источника. Эти отдельные измерения
не смешиваются с чистым приёмочным интервалом.

После теста выполнена пауза SPI **1200 ms** при закрытых USB streams:
Seed сообщил `SEED:SPI_TIMEOUT_RECOVER`, загрузился, поднял SPI/audio
и автоматически вернулся к 96k; sessions 8 -> 10, SPI CRC/sequence errors=0.
После fault-injection выполнен программный `seed reset` для чистой сессии.
Кнопки BOOT/RESET не нажимались. Ранее проверен также remote `seed boot`
с успешной DFU-записью и автоматическим запуском приложения.

## Программные проверки и исправления

- Обе прошивки собраны; отдельный compile/link пример экспортированного
  компонента также собран ESP-IDF 5.5.5.
- 12 unit tests анализаторов/CRC — PASS; CRC сверяется на 160 наборах
  с прежним bitwise алгоритмом и zlib, wire layout сохранён.
- 12 хешей переносимого компонента совпадают с активным; проверены LF/CRLF
  генерация DWC2 и отказ для неизвестной версии upstream.
- Seed: делители семейства 44,1/88,2, приоритеты DMA TX/RX/EOT, очистка UART
  NOLOAD SRAM, SPI timeout/IWDG и программное восстановление.
  Внешняя libDaisy не менялась.
  Использована установленная libDaisy с Git HEAD
  `265aae3ec3c79acfd4fd2a4b70980183285cc1ad`.
- P4: CPU counters читаются без `uxTaskGetSystemState`/сканирования стеков
  под scheduler lock; диагностика больше не задерживает USB completion.
- Capture startup backlog однократно ограничивается после первого IN
  completion; в steady state PCM не выкидывается для подстройки частоты.
- В WASAPI exclusive убран shared-only `GetNextPacketSize`;
  запись на диск выполняется после Stop, PCM копируется в заранее
  выделенную и затронутую RAM; проверяется devicePosition.

## Отозванные ранние PASS и пределы

Ранний анализатор v1 проверял RMS, разделение и нулевые серии, но не отклонял
ненулевые пропуски. Дополнительный фазовый анализ обнаружил в старых длинных
записях скачки по 10/20 ms. Поэтому `acceptance-v2-48k`,
`acceptance-v2-96k`, `acceptance-v2-formats-final` и
`acceptance-v2-multirate` сохраняются только как история диагностики,
**не как итоговая приёмка v0.2**. Итоговые результаты выше используют v2,
в котором разрыв фазы сам по себе означает FAIL.

192k на SPI 20 MHz реально испытаны: около 4300 transactions/s против
требуемых 6000, с потерями аудио. Формат исключён; рабочий потолок — 96k.
Ограничивает полный цикл READY/DMA/обработки, не пропускная способность USB HS.
FS, ASIO, аналоговый ADC/DAC, сквозная задержка и 30-минутный soak
не квалифицированы. Пять минут duplex выбраны по указанию пользователя.

# p4_uac2_stream — переносимый компонент v0.1.0

Неблокирующий транспорт USB Audio Class 2 для ESP32-P4. Это компонент USB,
не SPI-драйвер и не DSP. SPI-протокол приложения и прошивка Seed3 остаются отдельными.

Эту папку можно целиком скопировать в `components/p4_uac2_stream` другого
проекта ESP-IDF. Здесь сохранён снимок проверенного кода: 10 файлов
компонента совпадают с исходным рабочим проектом после нормализации CRLF/LF.
В 11-м файле, `port/patch_dwc2.py`, исправлена только проверка SHA для CRLF:
создаваемый C-драйвер совпадает с проверенной рабочей версией.
Контрольные суммы зафиксированы в [snapshot.json](snapshot.json).
Рабочая копия в проекте P4 не перемещалась и автоматически с экспортом
не синхронизируется. При будущих исправлениях обновляйте снимок осознанно.

## Фиксированный профиль

| Параметр | Значение |
|---|---|
| Платформа | ESP-IDF 5.5.5, ESP32-P4 rev1.x |
| USB | High Speed, встроенный OTG HS, порт TinyUSB 1 |
| Capture / playback | 2 / 2 канала, 48 000 Гц |
| PCM | signed PCM24, старшие 24 бита `int32_t`, младшие 8 бит нулевые |
| USB subslot | 4 байта, little endian, 24 valid bits |
| Интервал HS | bInterval=4, 1 мс |
| Capture-пакет | 47 / 48 / 49 stereo frames = 376 / 384 / 392 байта |
| Playback | asynchronous OUT, отдельный explicit feedback IN |
| Feedback HS / Windows | 4 байта Q16.16, frames / OUT packet, номинально 48.0 |
| Идентичность | VID 303A, PID 40A4, serial SEED3P4SPI2 |
| Драйвер Windows | штатный usbaudio2.sys |

48 кГц — единственная объявленная частота. Профиль FS предусмотрен в
дескрипторах, но acceptance относится к HS; FS отдельно не квалифицирован.

## API

```c
#include "p4_uac2_stream.h"

ESP_ERROR_CHECK(p4_uac2_init()); // асинхронная инициализация USB task

// В существующей SPI task, один раз на каждый принятый блок Seed3:
// adc и dac: interleaved L,R,L,R...; count — число stereo frames, не samples.
p4_uac2_capture_write(adc, count);
p4_uac2_playback_read(dac, count);
```

- `capture_write` вызывается с темпом Seed3 **даже при закрытом capture**:
  число полученных frames используется для измерения аудиочасов и feedback.
  Возвращает число принятых в ring frames; при закрытом входе возвращает 0.
  Часы источника учитывают весь переданный `count`, а не только принятые
  frames. Отброшенные frames не следует повторно отправлять через этот API.
- `playback_read` вызывается с темпом потребления Seed3. Возвращает число
  реальных frames, остальную часть буфера заполняет нулями. До prefill — нули.
- Для каждого направления допускается ровно один вызывающий поток:
  один producer capture и один consumer playback. API вызывается из task,
  не из пользовательского ISR. Буфер принадлежит вызывающему после возврата.
- Размер одного вызова: 1..512 frames; в текущем SPI-приложении 32.
- `p4_uac2_capture_active` / `p4_uac2_playback_active` означают alt 1,
  а не гарантию наличия звука или завершённых USB-пакетов.
- `get_stats`: независимые атомарные 32-битные счётчики, modulo 2^32;
  соседние поля могут отличаться на одну транзакцию. Для продолжительных
  тестов сравниваются unsigned дельты. `initialization_state == 2` — готов,
  `3` — ошибка инициализации.

## Владение буферами и задержка

`Seed/SPI -> capture SPSC -> task packet preparation -> DMA -> USB IN`

`USB OUT -> DMA -> task drain -> playback SPSC -> Seed/SPI`

По 512 stereo frames в каждом SPSC ring; каждый индекс меняет только его
владелец. Переполнение не перезаписывает непрочитанные данные: новые frames
отбрасываются и учитываются. Закрытие потока очищает tail его consumer-ом.

Capture начинает подготовку после 96 реальных frames. Контроллер длины
пакета поддерживает примерно 96 frames запаса плюс один DMA-пакет:
в сумме около 3 мс со стороны устройства. Playback prefill — 96 frames
(около 2 мс). Это не измеренная сквозная задержка: к ней добавляются SPI,
кодек, USB-планирование и буферы Windows/приложения.

Линейные DMA-слоты имеют 64-байтное выравнивание и 448-байтный stride;
размещены в internal DMA SRAM, не PSRAM. Четыре слота позволяют отделить
готовый, передаваемый и обрабатываемый буферы; capture готовит не более
двух пакетов вперёд. Feedback использует два раздельных 64-байтных буфера.
OUT-буфер CPU не изменяет: обработка mute/volume выполняется в отдельной
памяти task, чтобы не загрязнять линии DMA cache.

USB ISR обрабатывает только метаданные, счётчики, завершение/постановку DMA
и уведомление собственной USB task. В нём нет PCM-преобразования, malloc,
mutex, печати или пользовательского callback. Task работает на core 0,
существующая SPI task — на core 1. Control-запросы выполняются в USB task,
но в рабочем пути этой task нет диагностической печати: даже task-level
console log может заблокировать подготовку пакетов на десятки миллисекунд.
Приложение читает счётчики и печатает их из отдельной низкоприоритетной task.

## Планирование и восстановление

После completion следующий HS-пакет ставится за один microframe до
ожидаемого опроса хоста. Первый capture ожидает prefill; активный capture
никогда не ставит zero-length transfer. При нехватке данных передаётся
полный пакет тишины с отдельным счётчиком — это ошибка качества, а не
скрытое успешное восстановление.

Первый OUT синхронизируется по OUT-token-while-disabled. Чётность
не угадывается в момент SET_INTERFACE. ISO incomplete освобождает/повторно
ставит только соответствующий DMA-слот; watchdog отсутствия completion
реактивирует endpoint. Обработаны alt 0/1, suspend/resume и USB reset.
Ограниченные ожидания аппаратного abort при неисправности переходят
в переинициализацию USB-контроллера из task.

Feedback измеряет frames Seed3 относительно USB SOF, фильтрует оценку и
корректирует её по заполнению playback ring. Ресемплинга, дублирования
или удаления отдельных samples для подгонки частоты здесь нет.

Важно: внутренние расчёты HS выполняются в frames/microframe (номинально 6),
но Windows usbaudio2 при bInterval>1 ожидает feedback **на OUT-пакет**
(номинально 48). Перед передачей применяется множитель 8. Этот нюанс
совместимости также описан в [Linux u_audio_set_fback_frequency](https://github.com/torvalds/linux/blob/master/drivers/usb/gadget/function/u_audio.c).
Передача нескорректированного значения 6 приводит к игнорированию feedback
этим драйвером. `feedback_16_16` содержит именно отправляемое значение.

## Зависимости и перенос

`idf_component.yml` фиксирует TinyUSB 0.19.0~3. При CMake-конфигурации
`port/patch_dwc2.py` проверяет SHA-256 исходного DCD и создаёт частную
исправленную копию **в build**, не изменяя ESP-IDF или managed_components.
Неизвестная версия DCD останавливает сборку: обновление требует проверки
патча, а не отключения проверки хеша.

Порт включает MCNT для ISO IN DMA, восстановление адреса DMA после
incomplete, ограниченный abort, определение фазы OUT и OUT incomplete.
Для маленького feedback TX FIFO резервируется минимум 16 слов независимо
от 4-байтного размера USB-пакета.

Основания для решений: [Microsoft USB Audio 2.0](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/usb-2-0-audio-drivers),
[TinyUSB DWC2](https://github.com/hathach/tinyusb/blob/0.19.0/src/portable/synopsys/dwc2/dcd_dwc2.c),
[Linux DWC2: синхронизация ISO OUT](https://github.com/torvalds/linux/blob/master/drivers/usb/dwc2/gadget.c),
[CherryUSB: ограничения TX FIFO](https://github.com/cherry-embedded/CherryUSB/blob/master/port/dwc2/usb_dc_dwc2.c).

## Быстрая проверка пакета

В терминале ESP-IDF 5.5.5, из этой папки:

```powershell
python tests/verify_package.py
cd examples/compile_check
idf.py -DIDF_TARGET=esp32p4 build
```

Пример проверяет самостоятельную компиляцию компонента и публичного API.
Это **не готовая SPI-прошивка**: он не содержит драйвера Seed3 или источника
аудиочасов. Не прошивайте им работающую связку для проверки звука.

Проверка DWC2-патча, настройка rev1.x и интеграция в реальную SPI task
описаны в [инструкции](docs/INTEGRATION_RU.md). Утилиты записи, WAV и
готовая прошивка исходного стенда в этот исходный пакет не включены.
Повторный аппаратный прогон при упаковке не запускался: код транспорта
не менялся; подтверждение относится к снимку из [отчёта](docs/TEST_REPORT_RU.md).
